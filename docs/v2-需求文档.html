随时随地象棋助手（服务端 + iOS 悬浮提示）

背景与目标 总体架构 P1 服务端 P2 链路验证 App P3 完整 App 已定技术决策 风险清单 与 v1 的关系

版本：2.0　日期：2026年10月16日　仓库：Yxiansheng1/pikayu

背景与目标

v1（投屏 + TCHESS + 皮卡鱼）已在家庭局域网内跑通：iPhone 投屏到 Windows 笔记本，电脑端识别局面并显示引擎建议。v1 的限制是必须和电脑同处一个局域网。

v2 目标：脱离电脑，在任何有网络的地方，手机上下 JJ象棋 时能看到皮卡鱼的走法提示。最终形态为 iOS App：通过屏幕采集实时读取对局画面，以画中画"悬浮窗"显示提示；过渡形态为快捷指令截图版。个人练习用途。

分三期交付，每期独立可用、独立验收，后一期建立在前一期之上：

  • P1 服务端 + 快捷指令：纯 Python，先让"随时随地"以最低成本可用。
  • P2 链路验证 App：最小 iOS 壳，验证整条技术链路中唯一的高风险点。
  • P3 完整 App:画中画悬浮提示，目标体验。

总体架构

大脑全部放在家里电脑的 Python 服务里，手机端始终只做两件事：把画面送出去、把提示显示出来。

组件位置职责
棋盘识别家里电脑（Python）从截图/视频帧中检测棋盘与棋子，输出 FEN。YOLO 类检测模型，参考 TCHESS 开源的 yolov11 思路，针对 JJ 皮肤自行标注微调
引擎分析家里电脑皮卡鱼（复用 v1 已下载的 2026-09-06 通用版），UCI 子进程，固定思考时间
API 服务家里电脑FastAPI：收图 → 识别 → 分析 → 返回着法（中文记法 + 起终点坐标）
组网手机 ⇄ 电脑Tailscale 虚拟内网，免费、无公网暴露、手机装官方 App 即可
手机端 P1iOS 快捷指令截屏 → POST → 通知显示着法 → 删除截图
手机端 P2/P3自研 iOS AppReplayKit 屏幕广播采集 + 画中画(PiP)悬浮显示

运行前提：家里电脑开机在线（v1 已设置不睡眠）。电脑关机时手机端应得到明确的"服务不可达"提示，而不是无响应。

P1：服务端 + 快捷指令截图版

功能要求

  • HTTP 接口 POST /analyze：收一张 JJ 竖屏截图，返回 JSON：FEN、行棋方、建议着法（中文记法如"炮二平五"+ 起终点格子坐标）、分数、耗时。
  • 识别覆盖用户常用的 JJ 皮肤、红黑双方视角；对"非对局画面"（菜单、结算弹窗）返回明确错误而不是乱猜。
  • 行棋方判断：优先从画面特征（计时高亮等）推断；推断不了时按"截图者即将行棋"处理，并在返回中说明。
  • 引擎参数沿用 v1 结论：4~8 线程、固定时间 1~1.5 秒，服务端配置文件可调。
  • 快捷指令：一次触发完成"截屏 → 上传 → 通知显示着法 → 删除该截图"；建议绑定"轻点背面两下"。相册零残留。
  • 服务开机自启（Windows 计划任务或 nssm），崩溃自动拉起。

识别数据

  • 素材来源：5KPlayer 镜像录制（C:\Users\19705\Videos\Mirror Videos）抽帧 + 手机直接截图，覆盖 开局/中局/残局 × 红黑视角 × 动画瞬间 × 带弹窗干扰。
  • 标注量先小后大：先用少量样本验证 TCHESS 的 yolov11.onnx 直接复用的效果（GPL，个人使用），不达标再自行标注微调。训练可用 5060 PC。

验收标准

  • 识别：50 张覆盖上述矩阵的截图，FEN 全对率 ≥ 95%，错误样本记录原因。
  • 端到端：手机 4G/5G 网络下，双击背面到收到通知 ≤ 5 秒（目标 3 秒）。
  • 非对局画面 10 张，全部返回明确错误。
  • 连续使用一局棋（约 40 步）无需重启服务，相册无残留截图。

P2：链路验证 App（最小壳）

目的单一：验证整个 App 方案中唯一"做了才知道"的风险——ReplayKit 广播扩展能否在 50MB 内存限制内，把屏幕帧稳定回传到家里服务端。不做识别、不做提示、不做界面美化。

功能要求

  • iOS App + Broadcast Upload Extension：控制中心开启屏幕广播后，扩展以 1~2 fps 抽帧、压缩（缩放 + JPEG/HEIC）、经 Tailscale 发往服务端。
  • 服务端新增 POST /frame 收帧落盘，提供一个简单页面或日志确认帧到达与延迟。
  • App 主界面只显示：连接状态、已发送帧数、最近一帧缩略图（可选）。

工程与分发

  • 代码由 AI 生成（Swift），人只负责推送与装机验证；工程放 Yxiansheng1/pikayu 仓库 ios/ 目录。
  • 打包：GitHub Actions macOS runner 出未签名 IPA（本地无 Mac）。
  • 安装二选一，P2 期间实测后定：第三方企业签（浏览器安装 + 设置里信任，注意掉签风险）或 SideStore 免费自签（7 天自动续签，最多 3 个 App）。

验收标准

  • 打开 JJ 下棋 10 分钟，广播扩展不被系统杀死（内存超限会被静默终止，需实测）。
  • 服务端连续收到帧，帧间隔稳定，单帧从采集到落盘延迟 ≤ 2 秒（蜂窝网络）。
  • 发热、耗电record实际情况，不设硬指标。
风险出口：若 50MB 内存内无法稳定采集回传（P2 失败），退回 P1 快捷指令版为长期方案，P3 取消。此为立项时已接受的结果之一。

P3：完整 App（悬浮提示）

在 P2 壳上叠加目标体验。iOS 没有安卓式悬浮窗，悬浮效果用画中画（PiP）实现：App 把提示渲染成视频层浮在 JJ 上方。

功能要求

  • 服务端对收到的帧流自动识别局面变化（复用 P1 识别 + 稳定局面判定：连续 N 帧一致才算稳定，过滤动画/弹窗），局面变化后自动分析并把建议推回手机。
  • PiP 悬浮窗显示：当前识别的小棋盘 + 建议着法（箭头 + 中文记法）。新建议时更新画面。
  • 提示必须与当前稳定局面一致；识别失败或服务断开时悬浮窗显示明确状态，不显示旧建议。
  • 开关流程 ≤ 3 步：开 App → 开广播 → 开画中画，然后切到 JJ。

验收标准（对齐 v1 的同类指标）

  • 连续观察 30 次落子：漏识别、错局面、旧提示逐项记录；稳定画面出现后 ≤ 4 秒悬浮窗显示匹配建议（蜂窝网络，初始目标，未达标记录实际值再调）。
  • 红黑双方视角各测一局完整对局。
  • 异常恢复：断网重连、杀 App 重开、广播中断重启，均能在 1 分钟内恢复正常提示。

与 v1 的关系

  • v1（投屏 + TCHESS）继续作为"在家练习"的方案保留使用，两者互不影响。
